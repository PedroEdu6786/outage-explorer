- It means **switching to the new dataset and recording that the refresh succeeded in one database transaction**—both changes happen together, or neither happens. For example, suppose users currently read snapshot **A**, and a refresh builds snapshot **B**: 1. Upload B’s Parquet files to **S3** and verify them. 2. Start a PostgreSQL transaction. 3. Register B, change the active snapshot reference from A to B, and mark the refresh as **succeeded**. 4. Commit the transaction. This prevents inconsistent states such as “refresh succeeded” while A is still active, or B becoming active without its successful refresh record. **PostgreSQL stores the reference and refresh status; the analytical data stays in S3.** The S3 uploads happen before the transaction and are not part of it. - **PKCE** (“Proof Key for Code Exchange,” pronounced *pixie*) protects an OAuth login if someone intercepts the authorization code. It works like this: 1. Before redirecting to Cognito, your app generates a random secret called a **code verifier**. 2. It sends Cognito a SHA-256 hash of that secret—the **code challenge**. 3. After login, Cognito returns an authorization code. 4. Your app exchanges that code for tokens, supplying the original verifier. Cognito checks that it matches the challenge. An attacker who steals the authorization code cannot redeem it without the verifier. In phase 2, **PKCE S256** refers to that SHA-256 challenge method.
