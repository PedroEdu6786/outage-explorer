- Before running a query, the API copies the required data files into a temporary folder. It then records: **“This folder belongs to this execution; clean it up when that execution is finished.”** The problem is the order: 1. Create the folder and copy files. 2. Record who owns the folder. If the API crashes between those steps, the files exist, but the ownership record doesn’t. When the API restarts, cleanup checks its ownership records. Since this folder was never recorded, cleanup misses it. The abandoned files remain on disk. Repeated crashes can leave more folders behind until the disk fills up. Think of putting luggage in a storage room **before writing down its owner**. If you’re interrupted, the next person finds luggage with no record explaining why it’s there. Normal errors already trigger cleanup. This finding concerns abrupt crashes or forced termination. The intended fix is to **record ownership before copying the files**, so recovery knows what to clean up even if copying is interrupted. Your published data is unaffected; these are temporary copies.

<!-- codex-devlog:e23e1e0909ee4de600e328fa02360f7956786544bd5382f740176666d99a915d -->
- When a query needs a data file that isn’t cached locally, the API downloads it from S3. Currently it does this: 1. Download the **entire file into RAM**. 2. Once the download finishes, write it to disk. Think of filling a bucket with all the water before pouring it into a tank. You need a bucket big enough to hold everything. The better approach is to **download a small chunk, write it to disk, then repeat**. That way, RAM only needs to hold one small chunk at a time. Why it matters: the API shares that RAM with login, requests, and other work. Holding whole files uses memory unnecessarily. There is a configured file-size limit, so this is bounded; we haven’t demonstrated an out-of-memory crash. The fix is to stream into a temporary file while checking its size and checksum.
