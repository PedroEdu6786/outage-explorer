- **PKCE** stands for **Proof Key for Code Exchange**, pronounced “pixy.” It protects OAuth login by making a stolen authorization code insufficient to obtain tokens. [OAuth specification](https://www.rfc-editor.org/rfc/rfc7636.html) In our Cognito login flow: 1. **Our backend creates a random secret** called the `code_verifier` and keeps it for that login attempt. 2. It derives a SHA-256 hash from the secret, called the `code_challenge`, and sends that challenge when redirecting your browser to Cognito. 3. You sign in, and Cognito redirects your browser back with an **authorization code**. 4. Our backend sends Cognito both that code and the original `code_verifier`. 5. Cognito checks that the verifier matches the earlier challenge before issuing tokens. Someone who intercepts only the authorization code cannot complete step 4 successfully because they don’t have the secret verifier. **Your password proves your identity to Cognito. PKCE ties the code exchange to the application that started the login attempt.**

- It checks: **“Do we have enough allowed local-storage capacity to download all the missing files?”** It checks two limits: **1. Number of files** ```python len(self.store._objects) + len(new) ``` Already tracked files + files we’re about to download. If that exceeds `bounds.objects`, it rejects the operation. **2. Total size** ```python self.store._bytes + self.store._transient_bytes + sum(ref.object.byte_count for ref in new) ``` That adds: - Bytes already tracked. - Bytes currently reserved for temporary work. - Expected size of all missing files. For example: ```text Already tracked: 40 MB Temporary work: 10 MB Files to download: 70 MB Total: 120 MB Allowed: 100 MB → reject ``` `with self.store._lock:` keeps those counters from changing while the check runs. This uses **configured limits**, not a check of the machine’s actual free disk space. It rejects an oversized restoration before starting the downloads.
