- `epoch` is an **ownership version number** for the refresh worker. For example: 1. Worker A claims a refresh with epoch `5`. 2. Worker A loses its lease, and recovery advances the epoch to `6`. 3. Worker A resumes and tries to publish using epoch `5`. 4. The database rejects it because its ownership is outdated. This prevents a stalled or disconnected worker from later publishing over newer work. It’s a counter, **not a timestamp**.
<!-- codex-devlog:011e392d05a4e2fe4cf34602c4872fa015fad0f6957ead3c0d9018fcdfd3a776 -->
- A **lease** is a worker’s temporary right to own the refresh job. `lease_until` records when that right expires. While working, the worker periodically renews it. For example, if `lease_until` is `15:01:00`, the worker must renew before then. If it crashes and stops renewing, the lease expires, allowing recovery to recognize that ownership was lost. The **lease limits how long ownership lasts**; the **epoch identifies which ownership version is valid**. An interrupted, unpublished refresh still requires an explicit Admin retry.

- Yes, exactly. - **`refresh_coordination`** holds one shared row: which run is active (`active_run_id` → `refresh_runs.id`), which worker owns it, its lease and epoch, and which published generation readers use. - **`refresh_runs`** holds one row per refresh: who requested it, its configuration, progress, timestamps, and outcome. Those rows remain as history. The coordinator also **enforces ownership**, so an expired or outdated worker cannot update or publish the run.
