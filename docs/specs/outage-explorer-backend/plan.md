# Plan: Outage Explorer data and backend
> Status: draft — one replica and S3 + Parquet + DuckDB confirmed; mechanisms pending · Slug: outage-explorer-backend · Spec: ./spec.md

## Approach
The user selected one active backend replica, Amazon S3 as Parquet's durable home and DuckDB as the analytical SQL engine, serving all authorized clients through the API. [ADR-0001](../../adr/0001-s3-parquet-duckdb.md) records the rationale and alternatives. Python/FastAPI, HTTPX, PyArrow and SQLGlot remain candidate tools. The proposed query path authorizes the complete request, stages only permitted modeled snapshot objects, and loads them into an isolated DuckDB worker without bucket credentials or network access during user SQL execution. This staging path is a proposal, not part of the accepted tool selection. Backend hosting, operational database persistence, final data-loading strategy and SQL isolation still require selection and feasibility checks. (FR1–FR16, TR1–TR8)

## Components affected
- **Connector and validation** — fetch daily EIA metadata/pages, validate source-specific fields/keys and preserve raw evidence; bounded failures and safe reruns. (FR1–FR4, TR1, TR5)
- **Model and evidence** — three verified grain datasets, national fleet metric, reconciliation and retained findings inputs. (FR12–FR14, TR5–TR6)
- **Identity and policy** — persistent users with Argon2id password hashes, opaque expiring sessions, fixed operation/dataset permissions shared by every API path; SQLite remains a proposed metadata store for the selected single-replica deployment. (FR5–FR8, FR10–FR11, FR15–FR16, TR2, TR8)
- **Catalog and preview** — trusted schema metadata, applicable filters, verified unique ordering, generation-bound finite cursors, consistent error contract. (FR6–FR8, TR3, TR6)
- **SQL validation and isolated execution** — authorize nested references and functions before analytical reads; broad positive query coverage plus sandbox/resource boundaries. (FR6, FR9–FR10, TR3)
- **Refresh/publication** — application-owned background run, serialized refresh, validated interval replacement, durable outcome and atomic active-generation update. (FR1–FR4, FR11, FR15, TR6)
- **Delivery and verification** — reproducible environment, documentation, adversarial tests, independent metric checks, incremental commits and Engineering Notes. (FR1–FR15, TR4, TR7)
- **Deployment and durable storage** — one active backend replica, Amazon S3 bucket for Parquet independent of API/worker lifetimes, separately durable operational state, protected API transport and server-held credentials; backend hosting and operational persistence remain open. (FR16, TR7–TR8, AC13)

## Data model changes
- Raw and modeled Parquet remain separate. Model one relation per source grain; exact natural keys, parent relationships, column types and units are blocked on EIA investigation. Preserve source identifiers; do not impose guessed foreign keys or discard mismatches that are legitimate findings. (FR2, FR12–FR14, TR1, TR5)
- Proposed logical analytical names: `national_daily`, `facility_daily`, `generator_daily`, and `fleet_offline_share_daily`. These are product contracts, not asserted EIA field names. Viewer may use only national and national-derived metric relations; Analyst/Admin may use all analytical relations. (FR6–FR9, FR12)
- Metric candidate: same-day national offline capacity / national total capacity, expressed as a fraction or percentage with units explicitly documented. Source mapping, denominator meaning and missing/zero policy remain an evidence gate; no formula is treated as verified. (FR12, TR5)
- Each immutable generation has raw/modeled file hashes, schemas, verified keys, coverage, per-route/page retrieval windows, source parameters, row/validation counts, transformation revision and dependency/engine versions. Local publication does not claim a simultaneous EIA snapshot. (FR1–FR4, FR13–FR14, TR5–TR6)
- Operational metadata holds seeded users, session digests/expiry, finite preview cursor records, refresh runs/idempotency keys, trusted catalog metadata, generation references and evidence pins. A persistent SQLite database is the proposed single-owner store; the user has selected replica count, not the database engine. These records never enter user SQL. No role-management schema or UI beyond the three fixed roles. (FR5–FR8, FR11, FR16, TR2, TR6, TR8)
- Findings pin raw/model hashes, generation ID, exact reproduction query/command, transformation revision, dependency lock, metric definition and observed values; causal hypotheses are explicitly labeled. Pinned evidence survives ordinary retention cleanup. (FR13–FR14, TR4–TR6)

## Interfaces & contracts

### Shared deployment and storage — revised scope
- Clients connect to one authenticated API service and see the common published generation through role permissions. They never need Parquet copies, storage credentials or EIA keys. Protect remote credential/session transport; exact hosting, ingress and TLS mechanism remain open. (FR5–FR6, FR16, TR2, TR7)
- Persist both raw/modeled snapshots and necessary operational state outside disposable API/query containers. Document reattachment/recovery during replacement and verify it without contacting EIA. Backup/restore and acceptable deployment interruption must be stated for the selected topology; no zero-downtime or infrastructure-loss SLA has been promised. (FR4, FR16, TR8)
- **Selected topology/storage/engine:** one active backend replica serving multiple clients, Amazon S3 for persistent raw/modeled Parquet snapshots and DuckDB for analytical SQL. Backend analytical disk is disposable; necessary operational metadata has a separately durable lifecycle and is not an active SQLite database stored in the bucket. Replacement must prevent competing backend owners. Backend hosting is independent of the S3 selection. (FR11, FR16, TR6–TR8)
- One replica does not determine API process/thread count, concurrent user/query capacity or the number of disposable isolated query workers. Define refresh ownership and admission consistently across any internal processes; do not assume a process-local lock works merely because replica count is one. (FR3, FR8, FR11, TR3, TR6–TR7)
- **Deferred:** multiple replicas, cross-host publication/lease coordination and horizontal autoscaling. No multi-replica implementation is in scope. Object storage was chosen for independent persistence, not because multiple replicas are required. (FR16, TR7–TR8)
- Query preparation is trusted: authorize all query references/functions before fetching analytical objects. Resolve logical tables to exact object keys in one published manifest; download only permitted modeled inputs into bounded staging and verify manifest hashes. A trusted service identity owns bucket access; the user and SQL worker receive neither arbitrary object paths nor storage credentials/network access. Worker launching must fit the hosting platform; no host Docker daemon/socket is assumed. (FR6, FR9–FR10, TR2–TR3, TR7)
- Trusted DuckDB bootstrap materializes staged datasets as named in-memory tables, then disables external access and locks settings before executing validated user SQL. A simple view over a file is not equivalent to materialization when file access is disabled. Stage/download/load costs and memory amplification must fit the measured limits. DuckDB can also read S3 directly through `httpfs`, but that is an engine capability, not the selected worker path; changing to direct remote execution requires revisiting the credential/network boundary. (FR9–FR10, TR3)
- After execution, remove temporary inputs/worker state and release snapshot references; persistent bucket objects remain. Do not assume a shared cache, automatic bucket replication or offline availability during an object-store outage. EIA independence remains the availability promise. (FR4, TR3, TR8)
- Development should emulate the selected persistence and API contracts through environment configuration. The one-replica scope does not require multiple storage adapters or a distributed platform. (TR7–TR8)

SQLite, single-refresh details and the staging/worker steps below remain proposals. Query mounts in that proposal refer to temporary role-scoped staging, not the bucket itself. Direct remote reads versus staging remains open; reusable snapshots require measured justification and are not selected. Q2 concerns backend hosting, S3 configuration, operational persistence, runtime and budgets rather than replica count, storage provider or query engine.

### Authentication and shared authorization
- `POST /auth/login`: seeded credentials → opaque bearer token and expiry; invalid credentials return a uniform authentication failure. Use a password-hashing library; store token digests, not recoverable token values. Session TTL is documented before implementation. (FR5, TR2)
- Authenticate and look up the current role server-side on every protected request. Viewer is national-only; Analyst/Admin access all analytical datasets; only Admin may create/read refresh runs. No user SQL access to identity, session, run, filesystem or engine metadata. (FR6, FR15)
- Apply the same operation/dataset policy to catalog, preview, metric, SQL, cursor continuation and diagnostics. Fail before data retrieval; public errors do not include forbidden schemas, paths, records or raw engine output. (FR6–FR10, FR12, FR15)

### Catalog, previews, and SQL
- `GET /datasets`: authorized dataset IDs and column/type metadata only. Source/file paths are not part of the response. (FR7)
- `GET /datasets/{dataset}/preview`: applicable dates/facility filter, bounded page size, optional opaque cursor → schema, rows, generation ID and next cursor. Reject unsupported filter combinations explicitly. (FR8)
- Cursor records bind principal, generation, dataset, normalized filters, unique-key ordering, next position and a fixed proposed 15-minute expiry from the first page; continuation does not renew it. Reauthorize each page. Expired cursors return `410 cursor_expired` with a restart instruction; never silently change generations. Retain generation for the cursor's finite lifetime and every active query. All internal API processes must use the same cursor/reference state. (FR6, FR8, FR16, TR6, TR8)
- `POST /query`: one SQL statement → columns/types, rows, generation ID, truncation/limit metadata. Preserve normal SQL semantics; do not append an unsafe textual `LIMIT`. Row/byte caps apply while producing the response, and runtime limits apply regardless of output size. Errors distinguish authentication, denied access, unsupported query, malformed query, unavailable data, busy worker and resource limit. (FR9–FR10, TR3)
- The metric appears as an authorized analytical relation in catalog/preview/SQL; no separate metric service is required. Its national-only lineage must be verified before exposure to Viewer. (FR7–FR9, FR12)

### Query execution boundary
1. Authenticate; parse the full request without opening analytical files. Use a pinned SQLGlot DuckDB dialect and scope-aware relation resolution against trusted logical metadata. Traverse all branches, unused CTEs, aliases/shadowing, qualified/quoted names, nested expression subqueries, and function calls. (FR6, FR9–FR10)
2. Authorize every physical dataset and supported function/operator. Reject writes, schema/admin/configuration operations, multiple statements, external references, arbitrary table functions, dynamic SQL, extensions and engine metadata. Unknown/unresolvable forms fail closed. No user-derived planning, binding, `EXPLAIN`, or file loading before this check. (FR6, FR10, TR3)
3. Generate the validated statement and revalidate that exact representation before execution. Do not claim that two successful parses establish semantic equivalence: pinned-version composition/adversarial tests are a release gate. (FR9–FR10, AC7–AC8)
4. Admit a worker only after authorization and bounded trusted object preparation. Mount only authorized modeled files from request staging for the pinned generation, read-only. No bucket credentials, host home, raw extracts, secrets, identity DB, broad data-root mount or Docker socket enters the worker. Run without network, as non-root, with dropped capabilities, no-new-privileges, bounded scratch, process count, CPU, memory and lifetime. The trusted launcher uses fixed argument construction; SQL and identifiers cannot become shell, object-key or mount arguments. Platform support remains an open gate. (FR6, FR10, TR2–TR3, TR7–TR8)
5. Trusted bootstrap loads authorized product tables; disable external access, extension autoinstall/autoload and other unneeded access facilities, then lock engine configuration before user execution. A fresh worker avoids state leakage. Engine flags are additional controls, not a sandbox substitute. (FR6, FR9–FR10, TR3)
6. Parent enforcement terminates/reaps expired or failed workers, bounds result bytes and releases snapshot references. Reject work when the single query slot is occupied; no queue or user SQL cache. Bound startup/parse/output handling as well as engine execution. (TR3, TR7)

Mandatory SQL coverage includes compositions of joins, CTEs, nested/correlated subqueries, aggregations and windows, not just one isolated test per feature. The exact pure function/operator policy, set-operation coverage and recursive CTE handling must be documented and tested before implementation is called ready. A proposal to exclude recursive CTEs is still an open limitation, not an accepted reduction of user scope. (FR9, Q4)

### Refresh and publication
- `POST /refresh`: Admin-only inclusive `start_date`, `end_date`, idempotency key → `202` with run ID and status location. `GET /refresh/{run_id}` is Admin-only and returns state, requested/actual coverage, counts, validation outcome and published generation or safe failure reason. (FR11, FR15)
- Recommend one application-owned background ingestion task at a time with one refresh coordinator. Enforce ownership across any internal API processes and deployment replacement; no broker or service split is selected by implication. Same idempotency key and identical parameters return the existing run; changed parameters conflict. A different concurrent refresh returns busy/conflict. Disconnect does not cancel a run. (FR11, FR16, TR6, TR8)
- Persist states `accepted`, `running`, `succeeded`, `failed`, `interrupted`. Explicit retry uses a new key/run; no automatic source-read resumption on restart and no cancellation API initially. (FR11, TR6)
- Fetch and validate all three routes into a new immutable generation. Replace observations inside the requested interval; preserve previous observations outside it. Source-missing keys disappear from the new modeled interval only after the declared completeness checks pass, with removed counts and previous evidence retained. This represents observed source absence, not proof of intentional upstream deletion. (FR1–FR3, TR5–TR6)
- Completeness checks must account for all pages, stable requested ordering where supported, available totals, conflicting duplicate keys, required types and observed coverage. Unexpected emptiness, unstable retrieval or unexplained coverage reduction fails publication pending a documented source-backed policy. If repeated canonical retrieval comparisons are needed, scope and bound them; matching passes still do not prove upstream simultaneity. Do not ship interval replacement until actual API behavior supports the extraction contract. (FR1–FR3, FR13–FR14, TR5–TR6)
- Upload the complete immutable raw/modeled generation and manifest, verify objects/checksums, then commit the active-generation reference and run success together in durable operational metadata. A SQLite transaction remains proposed if SQLite persistence is selected; it does not make bucket writes transactional. New readers use the committed manifest, never incomplete prefix listings; prior queries keep their generation. Failed/incomplete uploads remain unpublished. Exclusive startup recovery reconciles interrupted runs, orphan local staging and unpublished objects before safe cleanup. (FR3–FR4, FR11, FR16, TR6, TR8)
- Retain current/previous generations, generations referenced by active queries/unexpired cursors, and evidence-pinned generations. Coordinate generation selection and reference acquisition with cleanup so a new reader cannot race reclamation. Cleanup is bounded and reference-aware; pinned findings are never removed by ordinary cleanup. A disk limit fails a new refresh rather than deleting required evidence. (FR3–FR4, FR8, FR13–FR14, TR6)
- Proposed freshness contract: no automatic update SLA; expose successful retrieval time and actual coverage. Admin chooses refresh range. Scheduling remains deferred. (FR11, TR6)

### Earlier single-host benchmark candidates — re-evaluate for shared deployment
| Concern | Candidate default / remaining measurement |
|---|---|
| Host | Earlier 2 CPU / 8 GiB / Docker estimate is not a deployment requirement; choose development and deployment envelopes after Q2 |
| SQL | One admitted worker; 1 CPU, 1 GiB memory, 10-second execution deadline, 30-second total worker lifetime |
| Results | 1,000 rows and 1 MiB serialized output; truncation reported |
| Preview | Fixed 15-minute cursor lifetime; exact page-size ceiling to set with query limits |
| Refresh | One run, 1 GiB worker budget, 2 GiB staging candidate; exact total deadline, page/retry/coverage ceiling and disk reserve set from source probe |
| Other limits | Request SQL bytes/AST depth, parser deadline, session TTL, process count and scratch quota to fix before exposed query implementation |

Prove combined backend/query/refresh memory and storage headroom on the agreed runtime. A refresh budget needs an enforceable process/container boundary or a proven bounded ingestion design; putting an unbounded background function in the API does not establish the budget. Numeric defaults may change through documented measurement, not silent failures or narrower SQL. (TR3, TR6–TR7)

## Implementation phases
1. **Source evidence and query feasibility** — inspect actual metadata/records; obtain >=30 days across all grains, verified key/unit/metric candidates, a reconciliation probe and three candidate real findings. In parallel prove composed FR9 queries and hostile requests under pinned engine/parser/container configuration. Exit only with measured host/limit assumptions and explicit SQL surface; report missing evidence instead of inventing findings. This is investigation, not a full second engine implementation. (FR1–FR3, FR6, FR9–FR10, FR12–FR14, TR3, TR5, TR7)
2. **Reproducible local data** — durable raw/model snapshots, validations, generation manifests, independent metric verification, fixed findings inputs and rerunnable reconciliation. Keep meaningful discrepancies; fail malformed extraction separately. (FR1–FR4, FR12–FR14, TR1, TR5–TR6)
3. **Authenticated free exploration** — seeded login, shared role policy, authorized catalog/preview/metric, finite cursors and isolated broad SQL; demonstrate arbitrary supported analytical compositions rather than prescribed investigations. (FR5–FR10, FR12, FR15, TR2–TR3)
4. **Controlled refresh and continuity** — implement the accepted interval/publication/run lifecycle, outcome polling, concurrent readers, restart recovery and reference-aware retention. Verify source revisions and partial failures against the documented contract. (FR1–FR4, FR8, FR11, FR13–FR15, TR6)
5. **Challenge rehearsal** — clean-host setup, offline browsing, full positive/negative role matrix, resource/crash tests, final three evidence-backed findings, schema/ER diagram, DECISIONS/FINDINGS/Engineering Notes and live explanation/debug rehearsal. Incremental commits and notes apply from phase 1. (FR1–FR15, TR4, TR7)
6. **Shared deployment rehearsal** — run one backend replica with separate clients, persistent storage and protected API access; replace API/query containers with EIA unavailable and verify shared data/permissions/recovery plus absence of overlapping owners. Deployment design belongs before dependent implementation even though this final acceptance rehearsal follows it. (FR16, TR7–TR8, AC13)

## Dependencies & integrations
- EIA API key from environment and access to real metadata/records; no live EIA investigation has been performed during this planning run. (TR1, TR5)
- Python/FastAPI for API and dependency-based auth; HTTPX for EIA HTTP; PyArrow for raw/modeled Parquet; SQLite for operational records; Argon2id via a maintained hashing package; pytest for verification. Exact versions must be pinned following feasibility. (FR1–FR15, TR1–TR4)
- DuckDB is selected; SQLGlot remains a proposed validator whose compatibility with the pinned engine must be tested. Docker remains a proposed isolation runtime; the deployable execution boundary and launcher depend on backend hosting. (FR6, FR9–FR10, TR3, TR7)
- Sources checked during planning: [FastAPI security](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), [HTTPX](https://www.python-httpx.org/), [PyArrow Parquet](https://arrow.apache.org/docs/python/parquet.html), [SQLGlot scope](https://github.com/tobymao/sqlglot/blob/main/sqlglot/optimizer/scope.py), [DuckDB security](https://duckdb.org/docs/current/operations_manual/securing_duckdb/overview), [Docker limits](https://docs.docker.com/engine/containers/resource_constraints/). These establish component capabilities, not application correctness.

## Risks & tradeoffs
- Parser/engine mismatch — exact generated-statement validation, pinned dependencies, positive compositions and adversarial corpus; revisit engine if FR9/FR10 cannot both be met. (FR9–FR10)
- Isolation complexity/startup cost — one local container per query is proposed to protect the mandatory role boundary; test performance and the real host before acceptance. Do not substitute an ordinary same-user subprocess and call it a sandbox. (FR6, TR3, TR7)
- Source revisions and pagination drift — metadata/real-data gate, route retrieval windows, conservative failed publication, retained evidence; no invented consistency promise. (FR1–FR3, FR13–FR14, TR5–TR6)
- Analytical mismatches versus malformed input — source-supported validation must preserve legitimate missing-parent/mismatched-sum observations for findings, while incomplete extraction blocks publication. (FR2, FR13–FR14)
- Evidence retention consumes disk — budget required, failed refresh under exhaustion, evidence never silently pruned. (FR3–FR4, FR14, TR6)
- Background refresh adds run state — accepted by the council as a small local lifecycle to survive client disconnects; persisted state is not an automatic durable queue or automatic restart. (FR11)
- Amazon S3, Parquet and DuckDB are selected; other stack and operational defaults remain recommendations. Empirical gates and Q1–Q4 are still open. No application code, tests or runtime proof exist yet. (TR4–TR7)
- One backend replica is confirmed and serves multiple clients. Its restart/replacement can interrupt API availability while durable data remains intact; exact interruption expectations remain open. Query admission, internal process ownership and worker launching still need concrete design. (FR16, TR7–TR8)

### Alternatives considered
- Rust/DataFusion: same parser/planner offers a real compatibility advantage, but does not remove complete reference/function validation or isolation. Retain as a revisit option if the recommended pair fails; no parallel full implementation. (FR9–FR10, TR7)
- Synchronous request-owned refresh: simpler response but ambiguous disconnect/recovery behavior; recommend application-owned background execution with polling. (FR11, TR6)
- In-process user SQL with parser/engine flags alone: insufficient execution isolation for the role and resource contract. (FR6, FR10, TR3)
- JWT/external auth service, distributed queue, cache and Delta: no requirement currently justifies their additional machinery. Shared deployment with one replica is required; backend hosting remains open. Multiple replicas and horizontal autoscaling are deferred by user choice. (FR5, FR11, FR16, TR1–TR2, TR7–TR8)

## Test strategy
- **AC1–AC2:** Recorded-page integration fixtures plus actual extraction checks; multipage completeness, malformed fields, identical/conflicting duplicates, repeat runs, revised/removed rows, partial source failure and empty-interval policy. (FR1–FR3)
- **AC3:** Disable upstream connectivity after ingestion; catalog/preview/metric/SQL still succeed from a pinned local generation. (FR4)
- **AC4–AC5:** Seeded login, invalid/expired/forged tokens, current role lookup, direct endpoint access and Viewer denial across catalog/preview/SQL/metric/cursor/errors; prove positive Analyst/Admin access. (FR5–FR9, FR12, FR15)
- **AC6:** Filter/order correctness, cursor tampering/wrong principal/filter mismatch, two pages around refresh, fixed nonrenewing expiry, new-reader acquisition racing cleanup; no duplicate/skipped results within a valid cursor and no deletion of a newly referenced generation. (FR6, FR8)
- **AC7–AC8:** Known-result composed joins/CTEs/correlated subqueries/aggregates/windows; validate generated SQL; unused CTEs, shadowing, quoted/qualified references, dynamic/table/external functions, metadata, write/admin attempts, multiple statements, oversized/deep SQL and limits. Instrument ordering to prove denied inputs do not open data, launch workers or reach engine planning. Verify exact sandbox configuration and physical Viewer mounts, not just mocked denial branches. (FR6, FR9–FR10, TR3)
- **AC9:** Admin-only trigger/status, idempotent requests, conflicting keys/concurrency, disconnect, failures, crash points around publication, restart/interrupted states, active readers, disk exhaustion and orphan cleanup. (FR3–FR4, FR11, FR15)
- **AC10:** Independently calculate metric from verified raw values, units and denominator; test missing/zero cases and national-only lineage. (FR12)
- **AC11:** Reproduce >=30-day reconciliation and three actual findings; repeat after refresh/cleanup using pinned files/versions; distinguish observed mismatch from unverified cause. (FR13–FR14)
- **AC12:** Fresh environment and supported local host rehearsal, combined refresh/query budgets, worker kill/reap, setup/auth/query/findings commands, required delivery docs and explanation/debug exercise. Documentation check is not a substitute for these runtime tests. (TR4, TR7)
- **AC13:** Verify one active backend replica; ingest once, query the common generation from independent clients with different roles, replace API/query containers while EIA is unavailable, then repeat requests and verify persistent publication/accounts/evidence plus declared session/recovery behavior. Replacement must not overlap active owners; internal processes must agree on ownership and state. (FR4, FR6, FR16, TR7–TR8)

## Assumptions
- Realistic shared deployment with one backend replica and Amazon S3 + Parquet + DuckDB are user-confirmed. Seeded accounts remain sufficient, frontend remains deferred, and backend hosting/operational-state persistence/availability SLA remain open. (FR16, TR2, TR7–TR8)
- SQLite and one refresh coordinator remain recommendations. If SQLite is selected, its persistent disk/backup lifecycle is separate from temporary analytical staging; object storage does not automatically persist identities/sessions/run state. Query isolation and platform-supported launching still need review. (Q2)
- Interval replacement, background refresh, retained evidence, finite cursor lifetime and numerical defaults are proposed resolutions, not silently accepted requirements. (Q1–Q2)
- Exact source model/metric and SQL function surface are investigated before dependent implementation. No real anomaly is claimed by this plan. (Q3–Q4)

## Open decisions
- **Q1 — user review:** accept manual background refresh, explicit inclusive interval replacement, preserve outside interval, retain delivered findings, show coverage/retrieval time rather than promise automatic freshness. Source feasibility still conditions replacement.
- **Q2 — one replica and S3 + Parquet + DuckDB resolved:** choose backend hosting, S3 region and security/retention/recovery configuration, durable operational database mechanism, development storage setup, deployment interruption behavior, protected transport, internal process/refresh ownership, isolated worker execution and measured capacities. Select remote reads versus staging after feasibility measurements; caching remains deferred. The remaining stack and an AWS compute service are not selected by ADR-0001.
- **Q3 — empirical:** actual fields/keys/types/units, metric denominator and missing/zero policy, relationships, source revisions/completeness and three real anomaly candidates.
- **Q4 — empirical/design:** pinned DuckDB/SQLGlot versions, complete supported expression/function/dialect contract, recursive CTE/set-operation policy, composed-query acceptance and exact pre-execution rejection proof.
- Draft spec + plan are reviewable; unresolved readiness items must remain explicit in any subsequent task breakdown. No implementation or file-level task list has been generated.
