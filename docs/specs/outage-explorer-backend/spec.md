# Spec: Outage Explorer data and backend
> Status: current backend requirements; implementation and acceptance tracked separately · Slug: outage-explorer-backend

Connector policy update: [ADR-0037](../../adr/0037-connector-initial-load-and-retention.md)
and the [connector spec](../data-connector/spec.md) define initial loading
and source-absence retention. Initial live loading uses
April 2–October 1, 2026 inclusive and requires usable output in all three grains.
Refresh retains absent keys and wholly excluded routes while other valid updates
proceed; wholly excluded refreshes keep the active generation unchanged.

The [data API requirements](../data-api/requirements.md) and
[HTTP contract](../data-api/http-contract.md) record the implemented endpoint
contract and its acceptance checkpoints. [ADR-0051](../../adr/0051-configured-http-refresh-range.md)
selects a configured inclusive range for the Admin HTTP refresh action.

## Problem
People exploring U.S. nuclear outages must manually reshape EIA records and reconcile national, facility, and generator observations. They need data available from our deployed backend's own storage, reproducible evidence, and reliable role boundaries while exploring freely. “Local” means ingested and controlled by our application rather than queried live from EIA; it does not mean an individual user's computer.

## Goal
Deliver the challenge's connector, analytical model, and authenticated backend with realistic development/deployment so all authorized users can explore the backend's stored datasets and reproduce actual cross-grain findings.

## Requirements
### Functional (EARS)
- **FR1:** WHEN ingestion is requested THE SYSTEM SHALL retrieve all pages in the requested daily period from the national, facility, and generator EIA nuclear outage routes.
- **FR2:** WHEN records are ingested THE SYSTEM SHALL derive required fields from API documentation or, where unspecified, consistently recurring collected attributes and identifying attributes; validate empty values, dates, numbers, keys and unexpected attributes against the declared contract; and exclude invalid records from modeled output with visible exclusion accounting and bounded transient raw evidence. ADR-0060 supersedes durable raw/evidence-graph retention: selected/retained rows preserve private provenance and exact calculation evidence in three unified resource files. Bounded field/nullability contracts and refresh quality responses are implemented; broader historical validation remains open. See [ADR-0023](../../adr/0023-exclude-invalid-source-records.md).
- **FR2a:** WHEN an Admin checks a refresh outcome THE SYSTEM SHALL include a visible quality report identifying source datasets, received records, excluded invalid rows, identical duplicates collapsed, modeled rows and exclusion reasons/counts, and clearly state whether data was published with exclusions. Keep run failures distinct from record exclusions and count excluded rows separately from potentially overlapping reasons. Report when all incoming records were excluded and existing data was retained without publication; identify older valid rows retained after invalid replacements and their reasons (ADR-0026). No additional approval step is required. The data API contract defines the response, with quality and exact publication descriptors stored in PostgreSQL. See [ADR-0025](../../adr/0025-admin-refresh-quality-report.md).
- **FR3:** WHEN ingestion is repeated THE SYSTEM SHALL preserve a valid locally queryable dataset without duplicate natural keys or corrupted published data, collapse identical observations to one modeled row and replace older values with the most recent valid observation. Within one retrieval, conflicting valid national observations for the same date use the last record in recorded source order (ADR-0034). ADR-0036 extends that fallback to `(period, facility)` and `(period, facility, generator)` in the bounded verification contracts; historical guarantees remain unverified. See [ADR-0024](../../adr/0024-collapse-duplicates-and-use-latest-values.md).
- **FR3a:** WHEN every incoming record is excluded THE SYSTEM SHALL keep the existing published data unchanged and expose errors/reasons without publishing an empty replacement. WHEN an invalid replacement can be matched to an older valid observation THE SYSTEM SHALL retain that older row and its provenance while accepting other valid updates. Initial loading requires usable output in all three grains under ADR-0037; subsequent refreshes retain absent prior keys and wholly excluded routes. See [ADR-0026](../../adr/0026-retain-valid-data-on-invalid-refresh.md).
- **FR4:** WHEN upstream EIA is unavailable after successful ingestion THE SYSTEM SHALL serve browsing and analytical queries from local data.
- **FR5:** WHEN a seeded persona completes authentication THE SYSTEM SHALL establish the corresponding Viewer, Analyst, or Admin identity through Amazon Cognito managed login using OAuth2 Authorization Code with PKCE, with a fixed one-hour application session by default, browser reopening within a valid session, no automatic renewal, and current-session logout (ADR-0018, ADR-0045). Session continuity across backend restarts/outages is not required.
- **FR6:** WHEN any data operation is requested THE SYSTEM SHALL enforce the caller's role before retrieving data or executing the query: Viewer may access national analytical datasets only; Analyst and Admin may access all analytical datasets. Apply this role policy consistently across all access paths using application-owned PostgreSQL users, roles and assignments (ADR-0016, ADR-0043). Users are seeded with exactly one role per user (ADR-0044); registration and Admin user management are excluded throughout implementation. Separate read/write/delete permissions, individual grants, ABAC and row/column policies are outside current scope (ADR-0043).
- **FR7:** WHEN an authenticated user requests the catalog THE SYSTEM SHALL return only authorized datasets with their columns and types.
- **FR8:** WHEN an authenticated user requests a preview THE SYSTEM SHALL return authorized records with date filters, an optional exact facility ID for facility/generator datasets, and deterministic backend pagination: 100 rows by default, initial configurable maximum 500, and a snapshot-bound cursor expiring 60 seconds after the first page (ADR-0059 supersedes the earlier ADR-0015 lifetime).
- **FR9:** WHEN a user submits a supported read-only analytical query THE SYSTEM SHALL execute it over authorized product datasets, supporting projections, filters, aggregations, joins, CTEs, subqueries, and window functions without requiring predefined investigations. Target DuckDB analytical feature support broadly; document exclusions only for demonstrated issues (ADR-0012).
- **FR9a:** WHEN a user submits a supported analytical query THE SYSTEM SHALL provide numbered result pages selected by positive `page` (1-based) and `page_size`, identified by `query_id` for subsequent requests, from one execution on one authorized snapshot, preserving supplied SQL semantics without injecting ORDER BY, LIMIT or OFFSET. Continuations must retain that execution’s result sequence and multiplicity, recheck authorization, and explicitly report expired/lost state or total-result truncation. ADR-0020 supersedes default ordering in ADR-0019; ADR-0021 adds numbered page selection with a fixed page size per execution. ADR-0022 keeps query-ID metadata in a bounded, expiring in-memory store, with no durability requirement or per-query PostgreSQL record. Expiration or store loss requires an explicit rerun with a new ID; never substitute page 1. Reclaim abandoned state and any orphaned result files. Store implementation, result placement, TTL, page-size defaults/maximum and resource budgets remain to be finalized.
- **FR10:** IF a query writes data, changes schema/configuration, accesses unauthorized sources, or has unsupported/unresolvable data access THEN THE SYSTEM SHALL reject it before execution.
- **FR11:** WHEN an Admin requests refresh THE SYSTEM SHALL perform ingestion in the background, expose its outcome, and automatically make the updated data active on successful completion without a separate approval or publish action. See [ADR-0003](../../adr/0003-admin-refresh-publication.md).
- **FR12:** WHEN an authorized user requests the daily fleet offline-capacity share THE SYSTEM SHALL provide a ready-made daily analytical dataset using national same-day `outage / capacity` (multiply by 100 for percent), with both source fields in MW and EIA's `percentOutage` shown alongside the calculated percentage from the same stored observation, without requiring the user to derive the formula or fetch live data for verification. Preserve calculation precision and round presentation to two decimal places with halfway values rounded up. Do not add match/mismatch labels or discrepancy flags, or exclude an otherwise usable observation solely because the percentages differ (ADR-0031). Required national values and positive capacity follow ADR-0027. The measure includes full outages and partial output reductions using reported national MW (ADR-0035); it does not establish a full-day average, outage duration, lost energy or cause. See [ADR-0006](../../adr/0006-daily-fleet-offline-share.md).
- **FR13:** WHEN the analytical delivery is evaluated THE SYSTEM SHALL provide reproducible reconciliation across all three grains for at least 30 days.
- **FR14:** WHEN the analytical delivery is evaluated THE SYSTEM SHALL provide at least three real EIA anomalies with periods, affected entities where applicable, observed values, product treatment, and reproducible evidence distinguishing observed facts from hypotheses.
- **FR15:** IF a caller without Admin permission requests refresh THEN THE SYSTEM SHALL deny the request before starting ingestion.
- **FR16:** WHEN authorized clients access the deployed backend THE SYSTEM SHALL serve their permitted datasets from the application's common published data without requiring client-side copies or EIA credentials.

### Technical / Non-functional
- **TR1:** Source data is EIA Open Data API v2 daily `us-nuclear-outages`, `facility-nuclear-outages`, and `generator-nuclear-outages`. Under ADR-0060, durable modeled output is exactly three unified resource Parquet files per generation. Raw/page/disposition inputs remain bounded and transient, superseding the earlier durable raw/evidence layout.
- **TR2:** OAuth2 is required; OIDC is not required (ADR-0017 supersedes the OIDC requirement in ADR-0014). Keep seeded challenge personas and local operational identity records. Amazon Cognito User Pools provides managed login and OAuth2 token issuance via Authorization Code with PKCE (ADR-0018). Explicit client configuration, token validation and opaque application-session mapping are implemented; comprehensive live acceptance evidence remains separate. Our own authorization tables determine application permissions (ADR-0016). Accepted application sessions last one hour by default, with no automatic renewal initially, independent concurrent logins, and current-session invalidation on logout. Secrets remain outside committed code; passwords must not be stored as plaintext. Cognito stores and verifies seeded credentials; the application keeps essential local identity mappings and role assignments (ADR-0043). Public registration remains disabled.
- **TR3:** SQL is bounded by documented result and execution-resource limits, and all supported dataset references must be authorized before execution. Accepted in [ADR-0007](../../adr/0007-bounded-parquet-query-execution.md): batch-based Parquet reads without mandatory full-dataset materialization, bounded memory and temporary disk, limited query concurrency, bounded result fetching, and query failure isolated from API availability. Accepted starting controls in [ADR-0013](../../adr/0013-initial-query-controls.md): one isolated analytical worker at a time, retryable busy responses, a 10-second execution deadline, and results capped at 1,000 rows or 1 MiB with explicit truncation. ADR-0020 adds pagination of one execution’s result without SQL clause injection; total caps remain the baseline until explicitly revised. Query pages default to 100 rows with a maximum of 500; ADR-0059 fixes preview/result lifetime at 60 seconds. Process-owned metadata and private result spools have admission bounds; measured capacity remains open. Worker/DuckDB memory sizes, separate disk quotas and preparation/overall deadline remain to be measured. Broad analytical syntax does not grant arbitrary filesystem, network, extension, metadata, or administrative access.
- **TR4:** Local setup, seeded accounts, environment configuration, automated tests, schema/relationships, assumptions, limitations, and decisions must be documented. Incremental history and Engineering Notes must identify AI contributions, a concrete AI mistake caught, and independent verification.
- **TR5:** Natural keys, required fields, types, units, relationships, metric mapping, and source revision behavior must be established from actual EIA metadata/records, not invented.
- **TR6:** Refresh coverage, freshness, concurrent-reader behavior and partial failure must be explicit. Use recent dates covering at least 30 days for reconciliation (ADR-0009); preserve findings inputs. Snapshot retention/recovery policy and automated deletion are deferred (ADR-0010). Admin-triggered background refresh and automatic publication on success are accepted in ADR-0003. [NEEDS CLARIFICATION: Q1 — initial loading dates are resolved in ADR-0037 and HTTP refresh dates in ADR-0051; broader source completeness and snapshot retention remain open.]
- **TR7:** Development must be reproducible locally and the application must support realistic shared deployment with one active backend replica, as selected by the user. The challenge's local live session is one supported environment, not the sole deployment target. [NEEDS CLARIFICATION: Q2 — finalize EC2 deployment configuration and deployed RDS connectivity, execution runtime and resource defaults for one backend replica.]
- **TR8:** Amazon S3 is the durable home for the three unified resource Parquet files under ADR-0060/0061 and DuckDB is the analytical SQL engine, as recorded in [ADR-0001](../../adr/0001-s3-parquet-duckdb.md). Backend analytical disk is disposable; [ADR-0008](../../adr/0008-local-parquet-file-cache.md) selects a bounded local disk cache of immutable modeled Parquet, scanned by workers with only authorized files and no network or S3 credentials. Necessary operational state must also persist independently of disposable application/query processes or containers, in PostgreSQL on Amazon RDS (ADR-0032), with explicit DSN/password/IAM configuration implemented; deployed host configuration remains separate. A restart/redeployment must not require another EIA ingestion. Amazon EC2 deployment is selected (ADR-0038); host configuration, deployed RDS connectivity and infrastructure SLA remain open; no EC2 instance is required for local development; one replica does not mean one client or one permitted concurrent request.

## Inputs & Outputs
- Accepted code organization: a layered Flask monolith under [ADR-0030](../../adr/0030-layered-flask-monolith.md). Follow the [structure and dependency rules](../../context/code-structure.md); concrete process topology remains open.
- Accepted stack: Python/Flask ([ADR-0028](../../adr/0028-python-flask-backend.md)), PostgreSQL operational storage on Amazon RDS ([ADR-0032](../../adr/0032-postgresql-on-rds.md)); EC2 deployment is selected in [ADR-0038](../../adr/0038-ec2-deployment-local-development.md). Cognito setup and the RDS connection are user-confirmed complete; application integration is implemented; deployment configuration and full runtime acceptance remain open.
- Modeling approach: EIA observations use analytical datasets with versioned schema contracts, accepted in [ADR-0002](../../adr/0002-analytical-dataset-contracts.md). Operational entities retain separate persistence; bounded analytical fields and keys are implemented in the grain contracts; broader historical validation remains subject to TR5/Q3.
- Inputs: EIA metadata and daily rows, requested ingestion dates, seeded login credentials, authenticated catalog/preview/SQL/refresh requests.
- Outputs: bounded transient raw inputs, three durable unified resource files, validation/refresh outcomes, authorized catalog schemas, filtered/paginated previews, bounded query results, daily fleet metric, reconciliation and anomaly evidence.
- Source field mappings and keys: Q3 is partially resolved by [ADR-0006](../../adr/0006-daily-fleet-offline-share.md): national metric fields, units and three-date formula agreement are verified. Bounded facility/generator contracts, merge policies and reproducible cross-grain findings are implemented. Historical completeness and capacity-vintage generalization remain open.
- SQL language: DuckDB read-only analytical features under [ADR-0012](../../adr/0012-duckdb-analytical-feature-scope.md), with appropriate unsupported-query errors and exclusions justified by demonstrated issues. [NEEDS CLARIFICATION: Q4 — verify compatibility, reference authorization and resource limits on pinned versions.]
- Exact request/response contracts belong to the design; no source column names are assumed here.

## Scope
### In scope
- Connector, local analytical model, backend authentication/authorization, catalog, preview, broad read-only SQL, Admin refresh, metric, findings, and reproducible delivery.
- Seed one user per fixed persona; Analyst/Admin access all analytical datasets, excluding identity/session data and engine internals.
- Shared deployment/development with one active backend replica, Amazon S3 for persistent Parquet and DuckDB for analytical SQL, accessible to users through the authorized API.

### Out of scope (non-goals)
- Candidate review, Admin validation/approval workflows and a separate publish action for refreshed data are excluded from the current scope (ADR-0003).
- Frontend implementation is owned by the separate `outage-explorer-web` repository under ADR-0039. Backend delivery alone is not the full challenge submission.
- Registration and Admin user management (endpoints and screens) are excluded throughout implementation; password-recovery screens remain excluded. Users and role assignments are seeded with essential local identity data. Separate read/write/delete permissions, individual grants, ABAC and row/column restrictions are excluded for now (ADR-0043). OAuth2 remains in scope; OIDC integration is not required under ADR-0017.
- SQL writes, schema/admin commands, arbitrary files/network sources, and user extensions; revisit only through an explicit change to the read-only product contract.
- Multiple backend replicas and horizontal autoscaling are deferred by the user's current scope; revisit for an explicit availability/capacity requirement. This does not exclude isolated query workers.
- Scheduled refresh, distributed processing, query-result caching and a custom-built authorization server have no established requirement; revisit only for measured needs or explicit scope changes. Deployment design is in scope; Amazon EC2 deployment is selected; its supervision/storage pattern remains to be finalized. Temporary query-result continuation state is required by FR9a and is distinct from caching results for reuse by other executions.
- Outage-type classification and event reconstruction; revisit only after source support and user value are established.

## Assumptions
- Existing product anchor and backend/data-only scope remain confirmed.
- Deadline/engineering budget is not a decision constraint, per user; this does not imply unlimited infrastructure or justify extra components.
- The user selected one backend replica and Amazon S3 + Parquet + DuckDB. Application-owned data serves all authorized users through a realistic shared deployment. EC2 deployment is selected; local development needs no EC2 instance. S3 development access is verified, and Cognito setup and the RDS connection are completed per user. Local PostgreSQL test setup and application integration are implemented. Database checks require an explicitly configured disposable DSN; their availability is not implied by implementation. EC2 deployment configuration remains pending Q2. Snapshot retention/recovery-policy work is deferred.
- Broad SQL means the selected dialect's supported analytical forms, not every vendor's syntax or every engine feature. No silent fallback to single-table-only queries is permitted.
- User has no prescribed Analyst investigations. This does not remove FR13/FR14 findings obligations.

## Acceptance Criteria
- [ ] **AC1:** Ingestion retrieves a complete selected period from all three routes across page boundaries. (verifies FR1)
- [ ] **AC2:** Documentation/data-backed field contracts detect empty, malformed date/numeric, missing-key and unexpected-attribute records; invalid rows are excluded with bounded transient raw evidence, durable selected/retained-row provenance under ADR-0060, and visible counts/reasons without alone failing the refresh. Identical duplicates across pages/files collapse; newer valid observations replace older stored values; safe reruns preserve uniqueness. For national within-retrieval conflicts, verify last-valid-record-wins in recorded source order, one modeled row per date, and repeatable replay (ADR-0034). ADR-0036 extends that fallback to `(period, facility)` and `(period, facility, generator)` in the bounded verification contracts; historical guarantees remain unverified. (verifies FR2, FR3; ADR-0023, ADR-0024)
- [ ] **AC2a:** The Admin refresh outcome exposes accurate dataset-level quality counts and exclusion reasons for clean input, invalid rows and duplicates; overlapping reasons do not double-count excluded rows. Publication with exclusions is explicit, incomplete/failed runs are not presented as complete, and existing Admin-only access is enforced. (verifies FR2a; ADR-0025)
- [ ] **AC2b:** Starting with an existing valid analytical generation, an all-excluded refresh leaves the active dataset unchanged and reports no publication plus exclusion errors/reasons. A mixed refresh retains an older valid row for an identifiable invalid replacement, updates other valid rows, excludes unmatched invalid rows and preserves uniqueness/provenance. Report retained-old-row counts distinctly from accepted new rows. (verifies FR3a, FR2a; ADR-0026)
- [ ] **AC3:** Catalog, previews, metric, and SQL remain usable with EIA unavailable after ingestion. (verifies FR4)
- [ ] **AC4:** All three seeded personas authenticate through Cognito managed login and the selected OAuth2 flow; invalid/expired/revoked sessions fail, current-session logout stops access, and direct requests cannot bypass application role policy. Verify trusted local-user binding and correct access-token validation under the selected OAuth2 design. (verifies FR5, FR6)
- [ ] **AC5:** Viewer catalog/preview/SQL/metric paths never expose facility or generator details; Analyst/Admin can retrieve authorized detail. (verifies FR6, FR7, FR8, FR9, FR12)
- [ ] **AC6:** Preview filters and stable page ordering return the expected authorized records; pages continue on their original data version across refresh or fail with explicit documented expiry, without silently mixing versions. (verifies FR8; TR6)
- [ ] **AC7:** Positive analytical queries demonstrate joins, CTEs, nested subqueries, aggregations, and window functions over permitted datasets; returned results match known inputs. (verifies FR9)
- [ ] **AC7a:** Concatenated pages match the same execution’s retained result, including duplicates, unordered queries, explicit ORDER BY/LIMIT/OFFSET, joins and aggregates. Numbered first/middle/final pages, direct page selection and repeat visits use the same execution and page size; invalid values, size mismatches, empty/out-of-range pages and foreign query IDs have explicit behavior. Refresh does not change an existing sequence; retries, expiry/lost state, revoked access and resource exhaustion have explicit behavior. Store loss between pages returns an explicit unavailable error, never page 1; an explicit rerun creates a new ID. Expiration reclaims abandoned metadata and any result files; orphan cleanup preserves active results and durable data. Enforce per-user/global memory and storage budgets. No pagination clause is injected and no query is silently rerun. (verifies FR9a; ADR-0020, ADR-0021, ADR-0022)
- [ ] **AC8:** Unauthorized references, writes, administrative operations, external-access attempts, and unsupported access forms are rejected before execution; limits are observable and enforced. (verifies FR6, FR10; TR3)
- [ ] **AC9:** Only Admin can refresh; the background run exposes its outcome and successful completion activates the updated data without another Admin action. Previous published data remains available during refresh and after failure; revised/removed/partially retrieved records follow the declared refresh contract. Existing queries finish on their original data version. (verifies FR3, FR4, FR11, FR15; TR6)
- [ ] **AC10:** Metric follows the agreed formula from stored national inputs and documented units; required-value/positive-capacity handling follows ADR-0027. Both percentages are available with two-decimal, halfway-up presentation, without agreement labels or discrepancy flags; source-percentage disagreement alone does not reject a usable observation or fail verification (ADR-0031). (verifies FR12)
- [ ] **AC11:** Reconciliation spans at least 30 days across all grains and findings contain three actual anomalies reproducible from identified inputs and commands, including after a later refresh and local cache eviction. (verifies FR13, FR14; TR6)
- [ ] **AC12:** A clean development setup reproduces authentication, data access, and findings using documentation; deployment/storage configuration is documented alongside decisions, schema, tests, and Engineering Notes. (verifies FR1–FR16; TR4, TR7)
- [ ] **AC13:** One active backend replica serves separate authorized clients from the same published data under their respective role permissions; replacing/restarting the backend and query containers preserves published data and recoverable operational state without another EIA fetch or overlapping active backend owners. (verifies FR4, FR6, FR16; TR7, TR8)
